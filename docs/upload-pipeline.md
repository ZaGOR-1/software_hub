# Release-file upload pipeline

## Scope

Phase 10 adds authenticated release-file intake into private quarantine storage.
It does not publish files, move them into the permanent software root or expose a
public download URL. Those state transitions belong to Phases 11 and 12.

The implemented route pair is:

```text
GET  /admin/releases/{release_id}/files/new
POST /admin/releases/{release_id}/files
GET  /admin/files/{file_id}
```

All routes require an active administrator session. The POST route additionally
uses the upload-specific session CSRF dependency.

## End-to-end flow

```text
browser multipart request
→ authenticated administrator session
→ Content-Length pre-check
→ session-bound CSRF verification
→ bounded Starlette multipart parsing/spooling
→ validate release existence
→ normalize original filename and extension
→ allocate UUID-only storage paths
→ disk-reserve check
→ bounded copy into application temporary storage
→ actual byte-count enforcement
→ SHA-256 calculation during the copy
→ bounded magic-byte sample collection
→ extension versus detected-signature assessment
→ atomic temporary → quarantine move
→ optional scanner in a worker thread
→ normalize administrator metadata
→ duplicate SHA-256 lookup
→ short SQLite transaction
→ ReleaseFile and audit metadata commit
→ private quarantine inspection page
```

## Streaming and memory behavior

FastAPI receives the file as Starlette `UploadFile`. Starlette streams multipart
content into a spooled file instead of loading the complete binary into Python
memory. Software Hub then seeks that framework-owned stream to the beginning and
copies it into its own private temporary file in configurable chunks.

The application-owned copy:

- runs in an `asyncio` worker thread so blocking filesystem I/O does not block the
  event loop;
- defaults to 1 MiB chunks;
- keeps only the current chunk and a bounded magic-byte sample in memory;
- calculates SHA-256 in the same pass;
- counts actual bytes independently of browser metadata;
- removes an incomplete application temporary file on failure.

This design is bounded-memory, but it is not a raw ASGI-body parser. The reverse
proxy must still enforce the same request limit in production so an oversized or
chunked request is rejected before extensive framework spooling.

## Multipart request limits

Before reading a hidden CSRF form field, the form parser is restricted to:

```text
maximum files:           1
maximum fields:          64
maximum text-part size:  64 KiB
```

`X-CSRF-Token` is checked before form parsing when supplied. This is the preferred
path for future JavaScript-enhanced large uploads. Plain HTML forms remain fully
supported through the hidden CSRF field.

`Content-Length` is rejected when malformed, negative or greater than:

```text
MAX_UPLOAD_SIZE + 2 MiB multipart overhead
```

The header is only a pre-check. The actual file size is enforced again while the
application-owned copy is written. Missing `Content-Length` does not bypass the
actual byte counter.

## Filename and path policy

The original filename is metadata only. It is normalized and validated by the
Phase 9 filename policy:

- Unicode NFKC normalization;
- extension allowlist;
- NUL, separators and control-character rejection;
- deceptive double-extension rejection;
- Windows reserved-name rejection;
- UTF-8 byte-length limit.

The display filename may differ from the original filename, but it must keep the
same validated extension.

Physical names and paths are always generated by the server. A stored path has
the form:

```text
7d/c7/7dc7f85a7db34e7198cb5510bc31e91a.zip
```

No request field can select an absolute or relative physical path.

## Supported signature checks

The initial allowlist is:

```text
.exe
.msi
.zip
.7z
```

Detection uses server-read bytes, not the browser-supplied MIME type.

| Extension | Detection |
|---|---|
| `.exe` | DOS `MZ` header plus a bounded `PE\0\0` offset check |
| `.msi` | Compound File Binary signature |
| `.zip` | ZIP local-file, empty-archive or split-archive signature |
| `.7z` | 7z signature |

The result is one of:

- `match`: detected type agrees with the allowed extension;
- `mismatch`: another supported type was detected;
- `unknown`: no supported signature was detected confidently.

The MSI check identifies the Compound File container. It does not fully parse the
Windows Installer database. Archives are not unpacked in the MVP.

## Initial file status

Files remain physically inside `QUARANTINE_ROOT` regardless of the initial
metadata status.

| Signature | Scanner | Initial status |
|---|---|---|
| match | clean | `ready` |
| match | unavailable | `ready` |
| match | error | `quarantine` |
| any | infected | `rejected` |
| mismatch | any non-infected result | `quarantine` |
| unknown | any non-infected result | `quarantine` |

`ready` means validation intake completed. It does not mean published or publicly
downloadable.

## Scanner abstraction

The scanner contract is:

```text
scan(path) → clean / infected / error / unavailable
```

The base configuration uses `UnavailableScanner`, so ClamAV is optional and the
application remains usable on a low-memory VPS.

When enabled, `ClamAVCommandScanner`:

- executes one configured executable name or path;
- never uses a shell;
- passes a fixed argument list;
- redirects stdin from `/dev/null`;
- captures output without persisting raw scanner text;
- applies a configurable timeout;
- executes in an `asyncio` worker thread.

Only a bounded, application-defined status message is persisted. Uploaded bytes,
scanner stdout and physical paths are not written to the audit log.

## SHA-256 and duplicates

SHA-256 is calculated while copying the file, avoiding a second full-file read.
The normalized digest is stored in the indexed `release_files.sha256` column.

A duplicate is not rejected automatically. Before metadata insertion, the service
looks up existing records with the same digest and stores the duplicate count in
the audit event. The private file detail page lists matching records with their
eager-loaded release metadata.

This policy permits one binary to be intentionally attached to multiple releases,
editions or architectures while still warning the administrator.

## Transaction and compensation model

No database transaction remains open while a large file is being received,
written, hashed, moved or scanned.

The database transaction starts only after quarantine placement and scanner
completion. It performs:

- release revalidation;
- duplicate lookup;
- `ReleaseFile` insertion;
- successful upload audit insertion.

If validation or metadata persistence fails, Software Hub attempts to remove both
the application temporary file and the quarantine file. A separate failure audit
is attempted without masking the original upload error.

A process or host crash can still occur between the atomic quarantine move and the
metadata commit. The future reconciliation command must detect this orphan rather
than deleting it automatically.

## Trust boundaries

Software Hub does not trust:

- browser MIME type;
- original filename as a path;
- `Content-Length` as the final size authority;
- an archive's internal filenames;
- scanner availability;
- metadata URLs as instructions to fetch content.

The source URL is validated as HTTP/HTTPS metadata and is never fetched server
side.

## Configuration

```text
SOFTWARE_HUB_MAX_UPLOAD_SIZE
SOFTWARE_HUB_ALLOWED_EXTENSIONS
SOFTWARE_HUB_UPLOAD_CHUNK_SIZE
SOFTWARE_HUB_UPLOAD_MAGIC_SAMPLE_SIZE
SOFTWARE_HUB_STORAGE_MIN_FREE_BYTES
SOFTWARE_HUB_CLAMAV_ENABLED
SOFTWARE_HUB_CLAMAV_COMMAND
SOFTWARE_HUB_CLAMAV_TIMEOUT_SECONDS
```

The application limit and the future Nginx `client_max_body_size` value must be
kept aligned.

## Deferred to later phases

- publish, disable, archive and permanent-delete actions;
- quarantine → permanent storage move;
- public UUID download endpoint;
- `X-Accel-Redirect` delivery;
- Nginx request-size and rate-limit configuration;
- icon upload;
- archive-content inspection;
- digital-signature verification;
- storage reconciliation and checksum recalculation CLI;
- background or scheduled malware rescanning.
